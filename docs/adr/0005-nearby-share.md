# ADR 0005：就近分享 = 内网链接 + 二维码，不做双端 P2P 协议

- 状态：已采纳（M3.5「就近分享」首个原型随 Android 落地）
- 日期：2026-11

## 背景

希望支持「把文件发给身边的人」。候选形态：

1. **双 App P2P**（快牙/AirDrop 类）：设备发现（mDNS/蓝牙）+ 双方装 App + 协商协议。
2. **局域网分享链接**（本决策）：发件方 App 临时起一个内网 HTTP 服务，生成
   「链接 + 二维码」，接收方**有 App 用 App，没 App 用浏览器**。

## 决策

采用方案 2，且刻意不做：

- ❌ 设备发现 / 配对（二维码即发现，URI 即配对）
- ❌ 自定义传输协议（HTTP Range 即是协议，浏览器/curl 全部兼容）
- ❌ 互联网远程互传（安全与中继成本高；远程交给 M3 云盘聚合）

具体形态：

- 发件：`crates/stream` 新增 `ShareServer`，bind 局域网接口（不再是 127.0.0.1），
  延续既有 token 防护；`/manifest.json` 供 App 接收方列清单，`/` 供浏览器直接点按下载；
  文件内容走既有 Range 分块语义。仅限文件（目录先压缩再分享），关闭页面/手动停止即焚。
- 收件：App 内「接收文件」粘贴/扫码拿链接 → 拉 manifest → 逐个 HTTP 分块拉取并
  经 VFS `write_range` 落盘——**目标目录可以是本地也可以是 NAS**（VFS 的既有能力）。
- 二维码为唯一「发现」机制：编码内容就是 URL 本身，不引入新密钥材料。

## 理由

- **接收零门槛**是决定性差异：对方不需要装任何东西（浏览器能收）；装了 App 则升级为
  批量 + 进度 + 落到任意后端。双 App 方案把「对方必须装 App」当成前提，推广成本极高。
- 复用度：`stream` crate 的 token、Range、http 框架原样复用；新增代码集中在 share 路由。
- 攻击面可控：token 随机生成（枚举不可行）、仅绑定当次选择的文件、生命周期随 UI。

## 代价与风险

- 二维码只能单向传达；同一 Wi-Fi 网段是前提（企业 AP 隔离场景无解，提示文案兜底）。
- 发件期间 App 需存活（与 Android 传输前台服务/M1 语义一致；iOS 受系统限制只能前台）。
- HTTP 明文：内网环境可接受，token 防列目录不防窃听；敏感文件仍建议走 NAS/云盘。
- 后续若做「App 对 App 增强」（续传、批量相册、传输中心任务化），manifest.json 已留好协议面。
